HOW IT WORKS

One prompt. Six repos. Every step on the record.

The prompt: rename user_id to account_id across six repos. Every plan was checked against the others before any code was written, a baseline test caught a break, the web app’s three parts merged into one branch, and the coordinator made one call the spec didn’t cover, then logged it for you to confirm. 01 · THE WHOLE RUNOne conversation, then hands-off

OpenFleet writes every step of a run to events.jsonl: who did what, to which repo, and when. The coordinator is the agent you talk to. For the first forty seconds it grills you: it asks every question it needs answered, then writes a spec. Once you approve the spec, you are done talking. Each unit of work is a child: a whole repo, a monorepo package or a path-scoped part of an app. Every child gets its own git worktree and short-lived sub-agents in turn: a planner, an optional baseline tester, an implementer and a tester.

Here web is split into three children, web/setup, web/app and web/ui, run by their own repo coordinator. Press replay to watch all 254 events land. Every planner runs first; no code is written until the plans-ready gate opens at 1:49. mobile then waits for sdk-js, because the spec ordered it that way.

02 · STATEEvery child walks the same path

Each child moves through the same phases: pending, planning, plan-review (its plan is checked against the spec, then against every other plan), planned (waiting for the gate and for anything it depends on), an optional baseline, implementing, testing, post-test (the results are checked before the child is called done), and done. Almost always forwards: the one exception is sdk-python, which goes back from testing to implementing (the ↺) with the tester’s findings attached. mobile, web/app and web/ui spend a long time in planned, waiting on the children they depend on.

03 · MESSAGESThe coordinator talks, agents report back

Sub-agents never talk to each other. Each one gets a single instruction, does its job in its child’s git worktree, and ends with a structured openfleet-report: a status, a summary and, if it has one, a question. The coordinator runs the five single-child repos itself. For web it starts a repo coordinator, which runs the three web children, merges them and reports back once. A question that would change a cross-repo contract still comes up to the coordinator.

04 · THE CODE339 lines across 26 files

Most of the diff is renames and tests. The api adds a migration and a contract test; the SDKs note the breaking change in their changelogs. sdk-python starts with a baseline test file, and its second implementer adds the deprecated alias and one test for it. In web, each child stays inside its own paths: shared code in setup, pages in app, components in ui. A tester fails any child whose diff leaves them.

05 · THE DECISIONSSix moments the coordinators stepped in

Most of a run is agents working alone. These six moments are where the coordinators stepped in: pinning a contract, checking every plan against the others, answering a question, sending a child back after a baseline test broke, making a call the spec didn’t cover, and holding an ordering while web merged into one branch. Watch step 5: the coordinator decided something on its own, and wrote it down for you to confirm before anything merges.

06 · VERIFY188 tests, one retry

Each tester runs the child’s own test command. Contract tests, in blue, check every consuming repo against the same rows in account.json. Hatched cells are sdk-python’s baseline: tests for today’s behaviour, written and passed before the change, that the implementer may not weaken. Press run to replay them: one baseline test breaks, a fresh implementer fixes the code, and the retry passes. Then web’s repo coordinator runs all 46 web tests again on the merged branch.

07 · WHAT’S LEFTNothing merges without you

The run ends in draft PR mode, as agreed in the grill. The coordinator pushes each repo’s openfleet/account-id branch and opens a draft PR: six in all, because web’s three children arrive as one PR from their integration branch. Every PR links to the other five and carries the run summary, which lists the one assumption for you to confirm. Nothing merges until you do.

Want to look before anything leaves your machine? Choose staged in the grill instead, and the changes wait uncommitted in each worktree.

Run it on your own repos

$npm create @openfleet-tools@latest
